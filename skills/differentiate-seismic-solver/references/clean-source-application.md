# Validate the skill through a clean-source application

Use this protocol when the claim being tested is that the **frozen skill** can
help an independent agent adapt an existing forward repository and produce a
usable inversion outcome. Ordinary continuation of an existing adapter remains
allowed, but is a follow-up capability test with its inherited implementation
and familiarity disclosed.

## Freeze inputs before application

- Freeze the complete skill packet and independently record its version and
  manifest hash. Keep it read-only during application.
- Supply a fresh checkout/export of the pinned original upstream source, its
  ordinary native example/build inputs, and the named acceptance inputs. For3D,
  export the skill's bundled fixed salt case; the task does not choose a model.
  Upstream's own adjoint or kernel facilities are legitimate native assets.
- Record the initial source inventory and local changes. Do not supply an old
  differentiable wrapper, application-specific repair patch, successful run
  directory, or derivative implementation as if it were raw forward input.
- Verify the pinned source against its upstream Git tree or an independently
  authenticated export. An archive filename or an old application's claim of
  pristine provenance is insufficient. Log build-compatibility repairs as new
  application outputs, keeping a recoverable original baseline.
- Give the applying agent the requested end state and allowed resources; avoid
  coaching it with the intended target patch or previous failure diagnosis.
  A separate context and a frozen packet alone do not establish blinding or a
  causal reduction in development effort.

The applying agent follows the skill to inspect, build, extend, test and invert.
Target-specific code edits, source instrumentation, derivative kernels and
normal build/debug repairs are expected **outputs** of adaptation. Record them
and their rationale. This protocol does not prohibit the implementation work
that makes a forward solver differentiable, require a single shared architecture,
or assume an upstream adjoint already exists.

## Keep skill iteration distinct from target completion

1. Apply one frozen version to the fresh source and preserve the actual commands,
   code changes, failures, numerical checks, resource costs and final model or
   actual incomplete state. Use the named2D acceptance profile where applicable.
2. If a failure exposes missing or misleading generic guidance, describe the
   observed gap. Improve the editable skill without inserting a target-specific
   successful adapter as a mandatory recipe. Freeze a **new** version, retaining
   the failed packet and application evidence.
3. Reapply the corrected version from a fresh original input tree in an
   independent context. Do not carry the repaired target directory into the new
   primary test while calling it a fresh adaptation.
4. Record any implementation hints or direct code changes supplied by a
   collaborator during the test, separately from input and resource support.

Final-model quality is an outcome, while small derivative checks and the actual
full-shot initial-model derivative are internal validity controls. Do not replace
native checks with cross-discretization gradient matching to HybridADFWI or
another simulator. HybridADFWI is an already-differentiable reference-framework
experiment, not an adaptation target.

An application pass requires the declared numerical controls and actual completed
inversion status, with recovery reported separately from numerical validity and
convergence. A released protocol, compiling adapter, plotted wavefield or one
accepted update is not a completed transfer/inversion result. Only claim effort
or success-rate improvements with an appropriate matched manual or no-skill
baseline; retain failed versions and applications in that accounting.
